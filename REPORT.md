## 1. Тема та мета роботи

- **Тема:** Конвеєр обробки запиту у NestJS (Request Processing Pipeline).
- **Мета:** Поглибити знання щодо внутрішньої архітектури життєвого циклу HTTP-запиту в NestJS; реалізувати та налаштувати всі ключові ланки конвеєра: проміжне програмне забезпечення (`Middleware`), охоронці (`Guards`), перехоплювачі (`Interceptors`), канали трансформації та валідації (`Pipes`) та фільтри винятків (`Exception Filters`); розробити механізм наскрізного трасування запитів за допомогою `X-Request-Id`; побудувати систему автентифікації на базі Bearer-токенів та рольового контролю доступу (RBAC) з використанням метаданих (`@Public()`, `@Roles()`); забезпечити профілювання тривалості виконання запитів із передачею заголовка `Server-Timing`; уніфікувати структуру помилок API відповідно до міжнародного стандарту RFC 7807 / RFC 9457 (Problem Details for HTTP APIs).
- **Обладнання та програмне забезпечення:**
  - ОС Windows 10/11;
  - Середовище розробки Visual Studio Code;
  - Node.js v24.21.0 LTS, npm 11.19.0, Git;
  - Фреймворк NestJS 12 (ES Modules, TypeScript 6);
  - RxJS (для асинхронних потоків в інтерцепторах);
  - Інструменти контролю якості: `oxlint` (статичний лінтер), `tsc` (перевірка типів);
  - Фреймворк тестування Vitest v4.1.11 (5 модульних та 43 наскрізних e2e-тести).

## 2. Архітектура конвеєра обробки HTTP-запиту в NestJS

Життєвий цикл кожного вхідного HTTP-запиту в розробленому застосунку проходить суворо визначену послідовність етапів:

```
Запит клієнта
      │
      ▼
┌───────────────────────────────┐
│ 1. Middleware                 │  RequestIdMiddleware: зчитує або генерує X-Request-Id, прив'язує до req
└───────────────┬───────────────┘
      │
      ▼
┌───────────────────────────────┐
│ 2. Guards                     │  AuthGuard (Bearer токен -> req.user), RolesGuard (@Roles перевірка прав)
└───────────────┬───────────────┘
      │
      ▼
┌───────────────────────────────┐
│ 3. Interceptors (до виклику)  │  LoggingInterceptor, TimeoutInterceptor: фіксація часу старту performance.now()
└───────────────┬───────────────┘
      │
      ▼
┌───────────────────────────────┐
│ 4. Pipes                      │  ParsePositiveIntPipe (перевірка id >= 1), ValidationPipe (перевірка DTO)
└───────────────┬───────────────┘
      │
      ▼
┌───────────────────────────────┐
│ 5. Handler (Контролер)        │  Виконання бізнес-логіки у контролері та відповідному сервісі
└───────────────┬───────────────┘
      │
      ▼
┌───────────────────────────────┐
│ 6. Interceptors (після)       │  Замір тривалості, встановлення Server-Timing, структурний лог у консоль
└───────────────┬───────────────┘
      │
      ▼ (у разі виникнення помилки на будь-якому етапі)
┌───────────────────────────────┐
│ 7. Exception Filters          │  ProblemDetailsFilter: перехоплення помилок -> application/problem+json
└───────────────────────────────┘
      │
      ▼
Відповідь клієнту
```

## 3. Реалізовані компоненти конвеєра

### 3.1. Трасування запитів: `RequestIdMiddleware`
- **Файл:** `src/common/http/request-id.middleware.ts`
- **Призначення:** Забезпечує наскрізне трасування запитів (Distributed Tracing).
- **Принцип роботи:** Перевіряє наявність вхідного заголовка `X-Request-Id`. Якщо він присутній і відповідає безпечному патерну regex `^[\w-]{8,64}$`, він використовується як ідентифікатор; інакше генерується новий криптографічний `randomUUID()`. Ідентифікатор зберігається у властивості `req.requestId` та обов'язково повертається клієнту у заголовку відповіді `X-Request-Id`.

### 3.2. Автентифікація та авторизація: `AuthGuard` та `RolesGuard`
- **Файли:** `src/auth/auth.guard.ts`, `src/auth/roles.guard.ts`, декоратори `public.decorator.ts`, `roles.decorator.ts`, `current-user.decorator.ts`
- **Принцип роботи:**
  - `AuthGuard` перевіряє заголовок `Authorization: Bearer <token>`. За допомогою `Reflector` перевіряє наявність метаданих `@Public()`. Якщо маршрут публічний (наприклад, `/auth/login`, `/health`), перевірка пропускається. Інакше валідує токен через `AuthService` та зберігає об'єкт користувача у `req.user`. Якщо токен відсутній або недійсний — повертає `401 Unauthorized`.
  - `RolesGuard` аналізує метадані `@Roles('admin', 'teacher', ...)` на рівні методу або класу контролера. Якщо користувач не має потрібної ролі, повертає `403 Forbidden`.

### 3.3. Профілювання та моніторинг: `LoggingInterceptor` та `TimeoutInterceptor`
- **Файли:** `src/common/http/logging.interceptor.ts`, `src/common/http/timeout.interceptor.ts`
- **Принцип роботи:**
  - `LoggingInterceptor` використовує RxJS `tap` для заміру часу виконання запиту (`performance.now()`). У разі успішної відповіді додає стандартний заголовок продуктивності `Server-Timing: app;dur=<ms>` та записує структурний рядок у журнал формату: `GET /api/v1/tickets -> 200 4.2ms [TicketsController.findAll] [req-id]`.
  - `TimeoutInterceptor` обмежує час очікування обробки запиту (за замовчуванням 5000 мс), викидаючи `RequestTimeoutException` (код 408) у разі перевищення ліміту.

### 3.4. Валідація числових ідентифікаторів: `ParsePositiveIntPipe`
- **Файл:** `src/common/http/parse-positive-int.pipe.ts`
- **Принцип роботи:** Перевіряє параметри шляху (`:ticketId`, `:commentId`). Дозволяє виключно цілі додатні числа (`^\d+$`, `value >= 1`). У разі передачі нуля, від'ємного числа або рядка повертає стандартизовану помилку `400 Bad Request` із вказанням імені параметра у тексті повідомлення (`Параметр "ticketId" має бути цілим числом >= 1`).

### 3.5. Стандартизована обробка помилок: `ProblemDetailsFilter`
- **Файл:** `src/common/http/problem-details.filter.ts`
- **Принцип роботи:** Глобальний фільтр винятків перехоплює всі `HttpException` та непередбачені помилки. Формує тіло відповіді відповідно до стандарту **RFC 7807 / RFC 9457** із типом вмісту `application/problem+json`:
```json
{
  "type": "about:blank",
  "title": "Необхідна автентифікація",
  "status": 401,
  "detail": "Потрібен заголовок Authorization: Bearer <токен>",
  "instance": "/api/v1/users",
  "requestId": "e492e854-47e0-410a-9d93-3b4737d6e6ea"
}
```
Для відповідей 401 автоматично додається стандартний заголовок `WWW-Authenticate: Bearer realm="helpdesk"`. Непередбачені винятки приховуються за загальним повідомленням із кодом 500, логуючи повний стек помилки на сервері для запобігання витоку вразливих даних.

## 6. Відповіді на контрольні запитання

### 1. Який точний порядок проходження HTTP-запиту крізь компоненти NestJS і чим обумовлена ця послідовність?
**Відповідь:** Порядок виконання: `Middleware` → `Guards` → `Interceptors` (фаза до контролера) → `Pipes` → `Controller Handler` → `Interceptors` (фаза після контролера через RxJS `tap`/`map`) → `Exception Filters` (у разі виникнення помилки).  
Ця послідовність є строго логічною: спочатку `Middleware` виконує базові HTTP-маніпуляції (парсинг заголовків, трасування `X-Request-Id`), потім `Guards` перевіряють автентифікацію та авторизацію, заощаджуючи ресурси процесора на обробку тіла неавторизованого запиту. Після цього `Interceptors` запускають таймери, `Pipes` перетворюють та валідують дані запиту, і лише валідні дані потрапляють у бізнес-метод контролера.

### 2. У чому полягає принципова різниця між Guard та Middleware у NestJS?
**Відповідь:** 
1. **Доступ до контексту виконання (`ExecutionContext`):** `Middleware` має доступ лише до низькорівневих об'єктів Express `req`, `res`, `next` і не знає, який саме контролер або метод буде викликано. `Guard` отримує об'єкт `ExecutionContext`, що дозволяє зчитувати декларативні метадані через `Reflector` (наприклад, анотації `@Public()` чи `@Roles()`).
2. **Інтеграція з DI:** `Guard` є частиною графу залежностей NestJS і може легко впроваджувати будь-які сервіси, тоді як `Middleware` діє на рівні маршрутизатора до входу в пайплайн обробки NestJS.

### 3. Для чого використовується заголовок `X-Request-Id` та чому важливо валідувати вхідне значення?
**Відповідь:** `X-Request-Id` є стандартом де-факто для наскрізного трасування розподілених запитів (correlation ID). Він дозволяє з'єднати в єдиний ланцюг усі події в системі моніторингу: логи шлюзу, бекенду, запити до баз даних та звіти про помилки від користувача. Валідація вхідного значення (наприклад, регулярним виразом `^[\w-]{8,64}$`) є критично важливою, оскільки клієнт може передати шкідливий рядок (спроба Log Injection / CRLF Injection, занадто довгий рядок або спеціальні символи), що могло б призвести до відмови в обслуговуванні (DoS) або викривлення записів систем моніторингу.

### 4. Як працює заголовок відповіді `Server-Timing` і які переваги він надає при оптимізації системи?
**Відповідь:** Стандарт `Server-Timing` дозволяє серверу передавати в браузер або клієнт метрики продуктивності виконання операцій у форматі `Server-Timing: app;dur=12.4, db;dur=5.1`. Клієнтські інструменти (зокрема панель Network у DevTools та API `performance.getEntriesByType('resource')`) автоматично відображають ці метрики на часовій шкалі разом із мережевими затримками. Це допомагає розробникам локалізувати вузькі місця: чи затримка спричинена мережею, чи часом виконання запиту всередині додатка або бази даних.

### 5. Що визначає специфікація RFC 7807 / RFC 9457 (Problem Details for HTTP APIs) та чому її використання краще за довільний формат помилок?
**Відповідь:** Специфікація стандартизує формат машиночитаних повідомлень про помилки HTTP API із типом `application/problem+json`. Вона визначає обов'язкові стандартні ключі:
- `type`: URI-ідентифікатор типу проблеми;
- `title`: короткий людиночитаний опис;
- `status`: числовий код HTTP;
- `detail`: детальний опис конкретної ситуації;
- `instance`: URI ресурсу, де виникла помилка;
- розширення (`requestId`, `errors`, `allowed`).  
Використання єдиного стандарту позбавляє клієнтських розробників необхідності писати специфічні парсери під різні ендпоінти та сервіси компанії.

### 6. Як `Reflector` взаємодіє з декораторами метаданих у NestJS для перевірки прав доступу?
**Відповідь:** Користувацькі декоратори (`@Roles('admin')`, `@Public()`) використовують функцію `SetMetadata(key, value)` для прив'язки користувацьких метаданих до функції-обробника або класу контролера. Клас `Reflector` надає методи (зокрема `getAllAndOverride<T>()` або `get<T>()`), які дозволяють `Guard` або `Interceptor` витягти ці метадані з контексту `ExecutionContext` для поточного класу та методу, об'єднати або перевизначити їх (наприклад, метод з `@Public()` перекриває класовий захист) та прийняти рішення щодо доступу.

### 7. Чому важливо використовувати глобальний фільтр винятків із приховуванням деталей для статусу 500?
**Відповідь:** Необроблені системні винятки (NullPointer, синтаксичні помилки SQL-запитів, помилки з'єднання з БД) містять конфіденційні дані: шляхи до файлів на сервері, імена таблиць, версії драйверів та уривки коду (stack trace). Відображення таких деталей клієнту полегшує зловмисникам проведення цільових атак. Глобальний фільтр безпечно записує повний стек у захищений серверний журнал разом із `requestId`, а клієнту повертає нейтральне повідомлення «Сталася непередбачена помилка» із цим самим `requestId` для звернення до служби підтримки.

### 8. У чому різниця між функціональністю `Pipe` та `Interceptor` у NestJS?
**Відповідь:** 
- `Pipe` призначений суто для **перевірки та трансформації аргументів методу** контролера (тіла `Body`, параметрів `Param`, запиту `Query`). Він працює безпосередньо з вхідними даними аргументів перед викликом методу і не контролює потік після завершення методу.
- `Interceptor` охоплює весь життєвий цикл виклику методу завдяки моделі RxJS. Він може втручатися як **до** виконання методу, так і **після** нього, трансформувати повернене значення, змінювати заголовки відповіді, заміряти час виконання, керувати кешуванням, обробляти таймаути або навіть повністю підміняти потік результату.
